# Answers · 0.2 self-check

> Not linked from the module. Answer first.

1. **URL to page.** The browser asks a DNS resolver for the address of the name (the resolver may walk root → `.com` → the site's own name servers, and caches the answer for its TTL). It opens a TCP connection to that address on port 443. The packets leave your network through the **default route**; if you have a private address, a **NAT** device rewrites the source to its public address. At the server's side a **firewall / security group** allows or drops the connection. Then the **TLS** handshake runs (certificate checked, keys agreed), the browser sends the **HTTP** request, and the server replies with a status code and a body.
2. **`10.0.0.0/20`:** 2^(32−20) = 2^12 = **4,096** addresses; **4,091** usable in an AWS subnet (5 reserved); it spans sixteen `/24` blocks (`10.0.0.0`–`10.0.15.0`), so the last address is **`10.0.15.255`**.
3. **`(6)`:** the name didn't resolve. Check the spelling, then `dig <name>` and `cat /etc/resolv.conf`. **`(7)`:** the connection was refused or there's no route. If it says "Connection refused", the machine answered but nothing listens on that port: check the port number and `ss -tln` on the server; if it says "Network is unreachable", check `ip route`. **`(28)`:** timeout, so packets are dropped or lost. Check the firewall / security group and the route table.
4. A new security group has **no inbound rules**, so all inbound traffic is dropped, and by default it **allows all outbound**. Rules only *allow*; there are no "deny" rules. Security groups are **stateful**: the reply to an allowed request is automatically allowed back out, so you never write a rule for replies. (A network ACL is stateless and checks each direction on its own.)
5. A private address can't be used on the internet, so replies to it would have nowhere to go. A **NAT gateway** has a public address: it rewrites outgoing packets to use it, remembers the connection, and rewrites the replies back. It only tracks connections that *started inside*; it has no mapping for a connection started from outside, so the internet can't use it to reach the server.
6. Docker's DNS only resolves names of containers on networks the asking container is attached to; the client was on a different network, so the name failed at the DNS step (`(6)`). By address, DNS isn't involved, so the packet was sent but dropped by Docker's network isolation and never answered: a timeout (`(28)`).
7. Default route: `ip route`. DNS server in use: `cat /etc/resolv.conf` (and the `SERVER:` line in `dig` output). What a name resolves to: `dig <name>`. Ports a machine is listening on: `ss -tln` (TCP) or `ss -tuln` (TCP and UDP).
